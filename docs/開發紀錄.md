## 階段 0:姿態演算法模擬(2026-09-13)

### 為什麼先做
「繞圈時機頭角度算得準不準」是整個產品的核心,而且在桌上測不出來. 先用合成數據驗證再寫韌體.

### 方法
`tools/sim_attitude.py`:腳本產生真實姿態(地面停放仰角 12° → 起飛 → 平飛繞圈(±3° 亂流擺動)→
每 60 秒一輪 [連續三個圓筋斗 / 直角筋斗(急轉約 390°/秒,9.5g)/ 倒飛] → 降落),
由運動學精確推導陀螺儀與加速度計讀值,加上零點,雜訊,馬達震動(0.35g),再餵給與韌體同一套演算法.
線長 18m,單圈 5.2 秒 → 21.7 m/s,向心力 2.68g,飛行 325 秒.

「真實規格」感測器另外加:升溫零點漂移約 0.5°/秒,**刻度誤差 2.5%,軸間耦合 1~1.5%**(MPU6050 規格 ±3%/±2%).

### 結果(真實規格感測器,最大誤差 / 均方根誤差,單位度)

| 演算法 | 平飛繞圈 | 連續圓筋斗 | 直角筋斗 | 倒飛 | 動作間平飛 |
|---|---|---|---|---|---|
| 只用陀螺儀 | 1.2/0.6 | 6.1/2.5 | 7.9/3.8 | 10.4/5.1 | 9.0/3.9 |
| 不補償向心力 Kp0.5 | 4.6/2.9 | 6.1/2.0 | 7.1/3.4 | 9.3/4.6 | 7.7/3.4 |
| **補償 Kp0.2** | 2.4/1.0 | 7.9/2.9 | 5.9/2.9 | 4.6/1.9 | 5.5/2.5 |
| **補償 Kp0.5** | 2.9/1.2 | 8.5/2.8 | 6.5/2.9 | 4.7/1.7 | 4.9/1.7 |
| 補償 Kp1.0 | 3.2/1.7 | 10.1/3.4 | 8.2/3.6 | 4.9/1.6 | 5.5/1.7 |
| 補償 Kp0.5,速度低估 20% | 4.0/2.6 | 7.0/2.7 | 6.4/2.9 | 8.7/4.5 | 9.3/3.8 |
| 補償 Kp0.5,速度高估 20% | 7.0/3.9 | 12.0/5.4 | 7.4/3.3 | 4.2/2.3 | 8.9/4.1 |

### 結論
- **只用陀螺儀會隨時間累積誤差**(刻度誤差 × 一直繞圈 + 翻筋斗),飛越久越糟,不可用.
- **向心力補償有效**,飛行中融合增益取 **0.3**(0.2~0.5 之間表現相近).
- 筋斗中最大 6~8° 是暫態(爬升掉速,加速度計的機頭方向讀值被減速量污染),動作結束就收斂,不累積.
  補速門檻預設 +20°,這個誤差量不會誤觸.
- 速度設定錯 20% 時均方根約 4°,仍可用. 所以「線長 + 單圈秒數」大概填對即可.
- 模擬時抓到一個模擬器自己的錯(加速度計真值取了矩陣的欄而不是列),已修正,不影響演算法.

### 設計重點
- **控制迴圈獨立成高優先權工作**:C3 單核心,參考專案實測網頁送整頁時主迴圈停 0.5 秒以上.
  飛行中不能被網頁拖住. 兩邊只透過加鎖的快照交換資料.
- 遙測印出單次控制迴圈最長執行時間(exec)與節拍最長延遲(late),之後加 WiFi 時用來確認沒被拖慢.
- I2C 逾時設 10ms,線斷掉時不會卡死控制節拍;連續 10 次(50ms)讀不到判定感測器故障.
- 相容晶片:WHO_AM_I 接受 0x68 / 0x70 / 0x98.

### 編譯結果
RAM 4.7%(15,460 bytes),Flash 18.1%(356,834 / 1,966,080 bytes),專案原始碼零警告.

### 燒錄與實機結果(2026-09-13,COM20 開發板)
COM20 原本跑 GG 的天氣/股票顯示器韌體,GG 確認這塊是測試開發板,可以直接蓋掉.

1. **感測器接線不在 GPIO5/6**:第一次燒錄 `IMU_FAULT`. 加了三個診斷指令
   `mpu`(重新初始化),`scan`(掃目前腳位),`scanall`(逐對換腳位掃描),
   掃到 **SDA=GPIO0,SCL=GPIO1,位址 0x68**. pins_config.h 改成 0/1(r2),不必重新接線.
2. **副廠晶片刻度誤差**:靜止時加速度大小讀 **1.12g**. 原本靜止判斷要求 |a| 在 1±0.12g 內,
   剛好卡在邊界,永遠判定沒靜止,陀螺儀零點學不到. 根因是條件訂錯 —— 靜止該看「窗內擺幅」,
   不是「剛好 1g」. 放寬成 ±0.3g(只排除自由落體與持續加速),imu.cpp r2.
3. 修正後:`still=1`,零點學到 +0.36/+0.86/+0.47 °/秒,扣掉後殘值 ±0.1 °/秒.
   平放 P=-0.8° R=-0.9°(零點學到前是 -1.4°,差的那 0.6° 正是陀螺儀零點 ÷ Kp 造成的穩態偏差).
4. 控制迴圈 `exec=809us`(I2C 讀 14 位元組約 0.8ms),`late=0ms`,電變 1000µs.

### 尚待 GG 實機確認
傾斜方向(機頭抬起 P 變正,左翼抬起 R 變正):第 2 階段做好監看網頁後,用手機直接看.
開發板的晶片裝向是任意的,方向不對時用 `orient` 指令(之後是網頁選單)調.

### 觀察
副廠 MPU6050 的加速度計誤差達 12%,會直接影響「水平時讀到幾度」. 規格已有「角度偏移」欄位讓使用者手動修正;
若實飛發現不夠,再考慮加六面校正. 目前不加(簡單至上).

### 實機測試結果(電腦無線網卡連板子熱點)
- 首頁 14.6KB,載入中位 103ms;狀態 API 中位 21ms,最長 48ms. 無頭 Edge 載入後各數值與飛機圖示旋轉正確顯示(JS 無錯).

### 重要發現:控制工作優先權必須是系統最高
C3 單核心. 控制工作原本優先權 5,實測被 WiFi 搶佔:

| 情境 | 優先權 5 | **優先權 24(採用)** |
|---|---|---|
| 開機穩定後閒置 30 秒 | 執行 1.1ms / 延遲 0 | — |
| 無頭 Edge 載入 + 輪詢 | 執行 5ms / 延遲 2~5ms | 執行 0.88ms / **延遲 0** |
| 電腦斷開再連上熱點(WPA2 握手) | **延遲 32ms** | 延遲 0 / 16 / 0ms |
| 網頁回應速度 | 首頁 123ms,API 21ms | 首頁 103ms,API 21ms(不變) |

剩下的 16ms 是 WiFi 驅動關中斷,任何優先權都擋不住. 開機時 WiFi 初始化有一次 77ms 停頓,那時不可能在飛行,無妨.
代價與約束:控制工作裡**絕不能有忙等迴圈**(會餓死 WiFi).

### 觸地偵測的關鍵問題與模擬
特技直角彎持續 8~10g,比觸地衝擊還大,只看 G 力大小必定把直角彎誤判成觸地 → 飛到一半開始降落.
改成「超出 0.3 秒低通基準、80 毫秒內結束的短尖峰」. `tools/sim_impact.py` 用階段 0 的特技飛行真值 + 馬達震動驗證:
- r1 抓到缺陷:尖峰期間凍結基準,動作後 G 力維持高檔時尖峰永遠結束不了(卡住 28 秒,期間觸地抓不到).
